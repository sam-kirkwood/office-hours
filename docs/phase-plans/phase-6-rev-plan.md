## Where we are

- **Phase 5-rev complete.** Full problem loop is end-to-end: survey → daily
  queue → problem view (hints, upload, parse, review, submit, feedback) →
  notebook. Skill tree shows the user's graph with adjacent nodes and a NodePanel

- **Paper tables exist** (`papers`, `paper_engagements`, `paper_answers`,

- **`queue_items` kind `paper_engagement`** is accepted by the schema but never

## Phase 6-rev goal

A paper can be ingested by the operator, suggested to users based on their
interests, pre-generated into a structured engagement (why-this, orienting
concepts, 3–5 questions), and worked through question-by-question with dialogic
responses from Claude. Multi-session resume works via `current_question_index`.
Completed engagements appear in the notebook with questions, answers, and any
free-form Q&A turns.

Out of scope: live arXiv search (v2.1+); bespoke paper recommendation ranking
(Phase 7-rev); operator admin surfaces (Phase 8-rev).

## Decisions locked in

Resolve these before execution. Don't re-litigate them during implementation.

| Decision | Choice | Why |
|---|---|---|
| Paper ingestion route | `POST /admin/ingest-paper` on the Python service, protected by `require_internal_token` | Keeps all DB writes in Python; Next.js calls it from an operator-only page; consistent with the internal-token auth pattern |
| Paper dedup key | Unique on `arxiv_id` (when present) and on `doi` (when present); soft-check `(lower(title), year)` when neither is available — log a warning but still insert | F7 from pivot-plan.md; unique constraints already in `20250010` migration |
| Paper engagement URL | `/paper/[engagement_id]` — engagement is user-specific; paper id alone doesn't anchor a session | Consistent with `/problem/[queue_item_id]` design |
| `questions_json` schema | `[{id: uuid-string, kind: "comprehension"\|"critical"\|"connective", prompt_md: string, order: int}]` — generated by Claude as a JSON array | F11 from pivot-plan.md; `paper_answers.question_id` references the `id` field |
| Number of questions per engagement | 3–5, chosen by Claude based on paper depth | Spec says "a few questions"; Claude picks; we validate `len(questions) in range(3, 6)` |
| When engagement is pre-generated | When `POST /suggest-papers` writes the `paper_engagement` queue item — immediately in the same request | Avoids a separate background trigger; acceptable latency since suggest-papers is already a background-style call |
| Paper engagement queue item `ref_id` | `paper_engagements.id` | F9 from pivot-plan.md |
| `paper_answers` one-per-question-per-engagement | Unique constraint on `(engagement_id, question_id)` — upsert on re-answer | Users can revise; the latest answer is canonical |
| Free Q&A (`paper_qa`) turns | Stored in `paper_qa` table; not part of `paper_answers`; unlimited turns | Structurally different from guided questions; kept separate |
| Notebook title for paper entries | `"{paper_title} — Reading"` | Parallel to `"{node_title} — Problem"` |
| `suggest-papers` trigger for Phase 6-rev | Called from the Next.js survey route (same pattern as `generateProblem` seeding) — on survey completion, call `POST /suggest-papers` for the user | Gives something to test without a separate scheduler; real scheduling is Phase 7-rev |

## Step 1 — FastAPI: papers ingestion

### New file
- `api/routes/ingest_paper.py`

### Schema additions (`api/schemas.py`)

```python
class IngestPaperRequest(BaseModel):
    title: str
    authors_json: list[str]       # e.g. ["Feynman, R.", "Hibbs, A."]
    year: int
    abstract_md: str
    arxiv_id: str | None = None   # e.g. "2301.07041"
    doi: str | None = None
    external_url: str | None = None

class IngestPaperResponse(BaseModel):
    paper_id: UUID
    created: bool  # False if a duplicate was found and returned
```

### Route flow

1. Auth check (`require_internal_token`).
2. Dedup check: if `arxiv_id` provided, query `papers.arxiv_id`; if `doi`
   provided, query `papers.doi`. On match, return the existing row with
   `created=False`.
3. Soft-check `(lower(title), year)` when no unique identifier: log a warning to
   stdout but do not block the insert.
4. Insert into `papers`. On unique-violation (race or concurrent call), re-select
   and return with `created=False`.
5. Return `IngestPaperResponse(paper_id=..., created=True)`.

### Tests (`api/tests/test_ingest_paper.py`)

| Test | What it verifies |
|---|---|
| `test_missing_bearer_returns_401` | Auth required |
| `test_happy_path_inserts_paper` | New paper row written; `created=True` returned |
| `test_arxiv_dedup_returns_existing` | Existing arxiv_id → `created=False`, same paper_id |
| `test_doi_dedup_returns_existing` | Existing doi → `created=False`, same paper_id |

## Step 2 — FastAPI: `POST /generate-paper-engagement`

### New files
- `api/routes/generate_paper_engagement.py`
- `api/prompts/paper_engagement.py`

### Schema additions (`api/schemas.py`)

```python
class GeneratePaperEngagementRequest(BaseModel):
    user_id: UUID
    paper_id: UUID

class GeneratedEngagement(BaseModel):
    why_this_md: str
    orienting_concepts_json: list[str]   # 3–5 concept names
    questions_json: list[dict]           # [{id, kind, prompt_md, order}]

class GeneratePaperEngagementResponse(BaseModel):
    engagement_id: UUID
```

### Route flow

1. Auth check.
2. Load paper by `paper_id` → `title`, `abstract_md`, `authors_json`, `year`.
3. Load user's `user_interests` → collect `node_id`s → load those nodes → collect
   `title` strings for the personalisation prompt.
4. `call_json(...)` with `GeneratedEngagement` schema:
   - `model=SONNET_MODEL`, `max_tokens=4096`
   - System: cached prompt from `api/prompts/paper_engagement.py`
   - User: paper metadata + abstract + user interests
5. Validate `len(questions_json) in range(3, 6)`; if not, raise 500.
6. Insert `paper_engagements` row:
   ```python
   {
       "user_id": str(body.user_id),
       "paper_id": str(body.paper_id),
       "why_this_md": generated.why_this_md,
       "orienting_concepts_json": generated.orienting_concepts_json,
       "questions_json": generated.questions_json,
       "state": "not_started",
       "current_question_index": 0,
   }
   ```
7. Return `GeneratePaperEngagementResponse(engagement_id=UUID(row["id"]))`.

### Prompt (`api/prompts/paper_engagement.py`)

System (cacheable):
```
You are preparing a science paper for a working professional to engage with.

Given the paper's abstract and the reader's current interests, produce:
1. why_this_md: 1–2 sentences explaining why this paper is relevant to this reader's specific interests. Be concrete — name their interests.
2. orienting_concepts_json: 3–5 key concepts the reader should have in mind before diving in. Short noun phrases.
3. questions_json: 3–5 questions to guide the reading. Mix types:
   - "comprehension": tests that the reader understood a specific claim.
   - "critical": asks the reader to evaluate a method, assumption, or result.
   - "connective": asks the reader to connect the paper to something they already know.

Output JSON matching this schema exactly:
{
  "why_this_md": "string",
  "orienting_concepts_json": ["concept1", "concept2", ...],
  "questions_json": [
    {"id": "<uuid>", "kind": "comprehension"|"critical"|"connective", "prompt_md": "string", "order": 1},
    ...
  ]
}

Generate a fresh UUID (v4) for each question id. Order starts at 1.
```

User (per-call):
```
Paper: {title} ({year})
Authors: {authors}

Abstract:
{abstract_md}

Reader's current interests: {interest_titles_comma_separated}
```

## Step 3 — FastAPI: `POST /grade-paper-answer`

### New files
- `api/routes/grade_paper_answer.py`
- `api/prompts/paper_answer.py`

### Schema additions (`api/schemas.py`)

```python
class GradePaperAnswerRequest(BaseModel):
    user_id: UUID
    engagement_id: UUID
    question_id: str    # the uuid string from questions_json[*].id
    user_response_md: str

class GradePaperAnswerResponse(BaseModel):
    claude_response_md: str
    next_question_index: int   # updated current_question_index; -1 = all done
```

### Route flow

1. Auth check.
2. Load `paper_engagements` by `engagement_id`; verify `user_id` matches; load
   `paper_id`, `questions_json`.
3. Load `papers` by `paper_id` → `title`, `abstract_md`.
4. Find question in `questions_json` by `question_id`; 404 if not found.
5. `call_json(...)` with `GradeResponse` schema (reuse from grade_solution):
   - `model=SONNET_MODEL`, `max_tokens=2048`
   - System: paper answer prompt
   - User: question + user response + paper abstract for context
6. Upsert `paper_answers`:
   ```python
   {
       "engagement_id": str(engagement_id),
       "question_id": question_id,
       "user_response_md": body.user_response_md,
       "claude_response_md": result.response_md,
       "submitted_at": now_iso(),
   }
   ```
   Use `on_conflict="engagement_id,question_id"` to allow re-answering.
7. Advance `current_question_index`: find the current question's order; set index
   to the next order value. If this was the last question, set `state='completed'`
   and `completed_at=now()`.
8. Return `GradePaperAnswerResponse`.

### Prompt (`api/prompts/paper_answer.py`)

System (cacheable):
```
You are a reading companion helping a researcher engage with a science paper.

Respond to the reader's answer to a guided question. Your response should:
- Acknowledge what they got right or interesting about their answer.
- Gently point out what they may have missed or could sharpen.
- Add one piece of context from the paper they might not have noticed.
- Keep it to 2–3 short paragraphs.

Never give away the "full" answer — keep the reader thinking.
Output JSON: {"response_md": "<your markdown response>"}
```

User (per-call):
```
Paper abstract:
{abstract_md}

Question ({kind}):
{prompt_md}

Reader's answer:
{user_response_md}
```

## Step 4 — FastAPI: `POST /paper-question`

### New file
- `api/routes/paper_question.py`

### Schema additions (`api/schemas.py`)

```python
class PaperQuestionRequest(BaseModel):
    user_id: UUID
    engagement_id: UUID
    user_message_md: str

class PaperQuestionResponse(BaseModel):
    claude_response_md: str
    turn_index: int
```

### Route flow

1. Auth check.
2. Load engagement; verify user_id; load paper_id.
3. Load paper → `abstract_md`.
4. Count existing `paper_qa` turns for this engagement → `turn_index = count`.
5. Build conversation history: load all `paper_qa` rows ordered by `turn_index`,
   interleave as `user`/`assistant` messages for the Claude call.
6. Direct `client.messages.create(...)` call (multi-turn, not `call_json`) with:
   - System: paper Q&A system prompt
   - Messages: history + new user message
   - `model=SONNET_MODEL`, `max_tokens=1024`
7. Log with `log_llm_call(...)`.
8. Insert `paper_qa` row: `{engagement_id, turn_index, user_message_md, claude_response_md}`.
9. Return `PaperQuestionResponse`.

System prompt (per-call, not cached due to paper context):
```
You are a reading companion for this paper: {title} ({year}).

Answer the reader's questions about the paper faithfully and concisely.
- Draw only on the abstract and the paper's domain knowledge.
- If you are unsure, say so.
- Keep responses to 1–3 paragraphs.
Output plain Markdown.
```

## Step 5 — FastAPI: `POST /suggest-papers`

### New file
- `api/routes/suggest_papers.py`

### Schema additions (`api/schemas.py`)

```python
class SuggestPapersRequest(BaseModel):
    user_id: UUID

class SuggestedPaper(BaseModel):
    paper_id: UUID
    queue_item_id: UUID

class SuggestPapersResponse(BaseModel):
    suggested: list[SuggestedPaper]
```

### Route flow

1. Auth check.
2. Load `user_interests` for user → collect node_ids → load those `nodes` → collect
   titles and slugs.
3. Load all `papers` (at most ~50 at current scale).
4. Use Haiku to score relevance: for each paper, ask Haiku whether the abstract
   is relevant to any of the user's interest topics. Shortlist top 3.
   - `call_json(...)` with a simple `{relevant_paper_ids: list[str]}` schema.
   - Pass all paper abstracts + user interest titles in one call (cheap at scale).
5. For each shortlisted paper, check if a `paper_engagements` queue item already
   exists for this user + paper. Skip if so.
6. For each new paper:
   a. Call `generate-paper-engagement` internally (direct function call, not HTTP).
   b. Insert `queue_items` row:
      ```python
      {
          "user_id": str(body.user_id),
          "kind": "paper_engagement",
          "ref_id": engagement_id,
          "state": "pending",
          "priority_score": 0.4,
          "added_reason": f"A paper related to your interest in {matching_node_title}",
          "time_estimate_minutes_low": 20,
          "time_estimate_minutes_high": 45,
      }
      ```
7. Return list of `{paper_id, queue_item_id}`.

## Risks to watch

- **Haiku relevance call in `suggest-papers` with no papers.** If the `papers`
  table is empty, skip the Haiku call entirely and return an empty list. The
  current step flow checks for this but the Haiku prompt must handle the case
  gracefully if a paper is added between the load and the call.

- **`questions_json` UUID generation by Claude.** Claude is asked to generate
  UUID v4 strings for question ids. These are not validated as proper UUIDs by
  the route — they just need to be stable string keys. If Claude produces
  non-UUID strings, `paper_answers.question_id` stores them as text anyway
  (it is a `text` column, not `uuid`). Validate the schema in tests only.

- **Multi-session resume index alignment.** `current_question_index` is 0-based
  array index into `questions_json`. When the user reloads mid-engagement, the
  page must display the question at that index and all prior answers. Off-by-one
  errors here are easy — write a test that advances through all questions and
  verifies the final state is `state='completed'`.

- **`paper_engagement` kind in `DailyView`.** The `KIND_LABELS`, `KIND_COLORS`,
  and `KIND_CTA` maps already include `paper_engagement` entries. Verify the
  button style matches the problem card style for consistency.

- **Survey latency from `suggest-papers`.** Adding a Haiku call + Sonnet
  engagement pre-generation to the survey route increases latency. Both are
  best-effort (`.catch(() => null)`). If latency becomes unacceptable, move the
  `suggest-papers` call out of the survey route into a separate trigger (e.g.,
  a Supabase edge function or a separate operator call). For Phase 6-rev, keep
  it in the survey route for simplicity.

- **`paper_qa` system prompt includes paper title but not full text.** We only
  have the abstract. Claude's Q&A responses will be limited to what can be
  inferred from the abstract and domain knowledge. This is intentional for v1;
  v2.1 may add full-text retrieval.
